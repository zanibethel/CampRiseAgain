# Custom Camp email aliases — draft
Uses existing verified receiving domain and webhook, without paid dedicated inboxes. Native info, volunteer and forms inboxes, support auth mail and existing reply aliases remain separate.
- Configure aliases, explicit active-admin mailbox ACLs and verified forwarding recipients. No default recipients or live alias seeded.
- Archive incoming plain text, HTML and attachment files in private storage; attachment download requires a fresh ACL check and short-lived signed URL. Display HTML in a sandbox with no remote images or scripts. Upload file cap 40 MiB per file, 100 files per message; body size limits reject over-limit messages rather than silently truncate. Provider download host is restricted; confirm actual provider CDN host in staging.
- Portal compose, replies, Sent and archive; delivery state shown. Forwarding reservations prevent duplicate attempts; ambiguous sends remain uncertain. No auto-retry for uncertain outcomes. Authorized admins can retry a confirmed provider 429 rejection up to three total attempts; pending or uncertain states require manual reconciliation. Gmail reply relay for custom aliases is NOT yet supported; use portal replies until verified sender authentication and relay archival are implemented.
- Release blockers: run CI on this revision, validate migration and private storage RLS against shared project policies, staging end-to-end provider tests incl. HTML/attachments, ambiguous-delivery reconciliation, and production approval. No live changes.

## Custom Gmail reply upgrade (draft)
New forwarded copies sent to verified forwarding recipients who are also active admins with mailbox access receive a unique private Reply-To capability. It expires after seven days and permits one text reply to the original sender. The same sender, current alias ACL, active account, verified forwarding membership, completed inbound archive and accepted forwarding delivery are required. Reserve the outgoing Sent record atomically before sending; a second use or repeated event cannot send twice. Never expose tokens in mailbox APIs or logs. Pending or uncertain sends require reconciliation. Native reply routes are unchanged. No reliance on spoofable authentication headers: a signed webhook authenticates the provider, not the email author. The token is a bearer capability; do not forward/share it. Attachment replies and HTML-only replies are not supported in this phase; use the portal for text and do not assume files have been sent. New emails only, existing copies are not retrofitted. Before deployment: test migration, real Gmail reply, expiry/replay/revocation, wrong sender, auto-replies, attachments, and native inbox regression. No live changes from this draft.
